# PJ-001 个人知识积累工程 · 全量综合设计与执行方案 v6.0-重构

> **一句话**：把王老师20年产业金融创业经验编译成可持续运行的个人知识操作系统——支持决策、辅助表达、传承认知。
> **核心原则**：先服务现实，再服务愿景 | 先沉淀判断，再追求全面 | 先形成复用价值，再扩大规模

---

## 第一部分：项目底层的「三个为什么」

### 1.1 为什么做这件事

不是做一个文档整理项目——市场上有无数笔记工具+AI能做到转写和摘要。

**这个项目的本质是：把认知资产化。**

- 跑过100多家银行，知道每家审批偏好、风控逻辑——这是资产
- 做过从0到1再到10的创业，知道什么模式能跑通——这是资产
- 跟数百个行业人物打交道，知道谁有什么资源、谁跟谁有关系——这是资产

这些资产现在在你脑子里。项目的目标是：把它们提取出来、结构化存储、持续迭代。

### 1.2 三个业务价值点

| 价值点 | 具体场景 | 如果做成了 |
|:-------|:---------|:-----------|
| **决策支持** | 见银行前，知识库告诉你"上次跟这家银行聊到什么程度、他们关注什么" | 少走弯路，每次沟通都有历史参考 |
| **表达增强** | 写朋友圈/见投资人时，知识库提供结构化的观点素材 | 不需要每次从零组织语言 |
| **认知传承** | 合伙人/员工/未来数字人能够理解你的业务逻辑 | 你的经验不再只是你一个人的 |

### 1.3 不做边界

| 不是 | 是 |
|:-----|:----|
| 不是知识管理工具选型 | 是用已有工具（Obsidian）解决知识沉淀问题 |
| 不是学术论文知识库 | 是**创业决策支持**系统，聚焦判断和行动 |
| 不是简单录音转文字 | 是录音→判断→决策→行动的完整链路 |
| 不是一次交付 | 是5-10年持续生长的知识生命体 |

## 第十部分：增量更新机制（append-only Master层）⭐ 重构核心

### 10.1 根因：为什么覆盖模式是错的

**旧模式问题**：
- p3_aggregate.py 每次全量覆盖 persons_master.json
- 新录音处理后，已有的Person页被覆盖，旧数据丢失
- 每次批处理都在加剧数据损失

**正确模式**：
- Master数据只追加，不覆盖
- 每个实体的每次观察作为独立条目追加
- 新旧数据共存，支持历史追溯

### 10.2 append-only observations 结构

```json
{
  "persons": {
    "李洋": {
      "name": "李洋",
      "primary_role": "unknown",
      "primary_org": "unknown",
      "observations": [
        {
          "meeting_id": "20220401-李洋与供金部讨论商票",
          "role": "深度数科战略负责人",
          "org": "深度数科",
          "relation_to_wang": "业务伙伴",
          "timestamp": "2026-05-11T10:00:00",
          "source_candidate": "20220401_原文.json"
        },
        {
          "meeting_id": "20220419-深度数科与浙商银行交流",
          "role": "票据业务负责人",
          "org": "深度数科",
          "relation_to_wang": "业务伙伴",
          "timestamp": "2026-05-11T10:05:00",
          "source_candidate": "20220419_原文.json"
        }
      ]
    }
  },
  "count": 63,
  "last_updated": "2026-05-11T10:05:00"
}
```

### 10.3 persons_master.json 设计原则

1. **防重**：同一meeting_id+同role的obs不重复追加
2. **可追溯**：每个obs带source_candidate来源文件
3. **时间戳**：每个obs带timestamp，支持时间排序
4. **冲突检测**：新obs与历史obs矛盾时标记contradiction=true

### 10.4 meetings_master.json 结构

```json
{
  "meetings": {
    "20220401-李洋与供金部讨论商票": {
      "date": "20220401",
      "persons_mentioned": ["李洋", "王老师"],
      "orgs_mentioned": ["深度数科", "供金部"],
      "key_judgments": ["贷转票是核心机会"],
      "value_grade": "A"
    }
  },
  "count": 197,
  "last_updated": "2026-05-11T10:05:00"
}
```

### 10.5 p3_aggregate_append.py 核心逻辑

```python
# 伪代码
def append_observations_to_persons(master_data, new_candidates):
    for cand in new_candidates:
        for p in cand.get("persons", []):
            name = p.get("name", "")
            obs = {...}  # 构造新observation
            
            # 防重：同meeting+同role不重复
            existing = persons[name]["observations"]
            is_duplicate = any(
                o["meeting_id"] == mid and o["role"] == obs["role"]
                for o in existing

```

### 10.6 recompile_person.py：从Master重编译Person页

**触发场景**：
- 用户查询某人物时，从observations实时重编译
- 批量重建所有Person页（初始化时）
- 增量更新后单页重编译

**编译逻辑**：
1. 加载persons_master.json中该人的所有observations
2. 按时间排序
3. 聚合最新role/org/relation_to_wang（取最后一次的值）
4. 收集所有关联meeting_id
5. 生成v6.0格式Person Wiki页

## 第十一部分：双层Query架构 ⭐ 重构核心

### 11.1 架构概览

```
用户query
    ↓
【L1实体导航】（80%场景，纯规则，无LLM）
    ↓ 命中
返回：实体概况 + 相关Meeting列表
    ↓ 未命中
【L2语义综合】（20%场景，MiniMax M2.7调用）
    ↓
返回：综合回答 + 引用来源
```

### 11.2 L1实体导航（entity_nav.py）

**无LLM，纯规则匹配**：
1. 从query中提取可能的人名/公司名（正则匹配）
2. 在persons_master.json中查找人名匹配
3. 在organizations_master.json中查找公司名匹配
4. 找到则返回：实体概况 + 关联meeting列表
5. 找不到则返回None，交L2处理

**L1覆盖的高频场景**（占80%）：
- "王老师与深度数科有哪些合作？" → 查李洋的observations
- "上次跟浙商银行聊了什么？" → 查浙商银行的observations
- "鞠世颖是谁？" → 查鞠世颖的observations

### 11.3 L2语义综合（kb_retriever_v2.py）

**L1失败后的兜底层**：
1. 收集L1返回的Meeting页内容片段
2. 调用MiniMax M2.7-highspeed进行语义综合
3. 生成结构化回答，附引用来源

**触发条件**：
- query中无明确实体名
- 跨多个实体的综合问题
- "我最近的判断有什么变化？"

### 11.4 为什么不依赖向量RAG

**根因**：中文分词问题
- 现有向量模型中文分词不准
- "供应链金融"可能被切分为"供应"+"链金"+"融"
- 检索结果0命中但内容明明存在
- GPT报告建议：简单匹配优先，RAG作为降级方案

### 11.5 kb_retriever_v2.py 实现

```python
def query_wiki_v2(query_str):
    # L1：实体导航
    results, status = entity_nav(query_str)
    if results:
        return results, "L1命中"
    
    # L2：语义综合（LLM调用）
    return semantic_synthesis(query_str), "L2语义综合"
```

## 第十二部分：ReviewQueue最小化机制 ⭐ 重构核心

### 12.1 三级分流

| 级别 | 触发条件 | 处理方式 |
|:----|:---------|:---------|
| **自动通过** | frontmatter格式/索引追加/低风险 | 不入队列，直接落库 |
| **批次确认** | 新实体页/新judgment草案/新判断 | 入staging区，批量通知 |
| **强制确认** | 覆盖高价值判断/标记冲突/删除 | 入review_queue，逐条确认 |

### 12.2 批次确认流程

```
每批处理完成（每日或达到N条）
    ↓
生成staging快照（SYSTEM/staging/）
    ↓
推送飞书/微信通知（"X条待确认，Y条自动通过"）
    ↓
王老师扫一眼，判断是否全部通过
    ↓ 确认
staging区数据 → 正式落WIKI库
```

### 12.3 staging区数据结构

```
SYSTEM/staging/
├── 2026-05-11/
│   ├── batch_001.json   # 本批次的完整数据
│   ├── persons_new.json # 新增人物
│   ├── orgs_new.json    # 新增机构
│   ├── judgments.json    # 新增判断
│   └── meetings.json     # 新增/更新会议
└── confirmed/           # 已确认的批次（归档）
```

### 12.4 review_queue.py 实现

- 读取SYSTEM/staging/中待确认批次
- 生成飞书/微信通知
- 用户确认后执行落库操作
- 归档已确认批次到confirmed/

## 第十三部分：Orchestrator最小化 ⭐ 重构核心

### 13.1 设计原则

**最小化复杂度**：
- 不用复杂的调度框架
- 用cron定时 + 文件系统事件驱动
- Python脚本 + nohup后台运行

### 13.2 三层触发机制

```
① 事件触发（新文件到达）
   inotifywait监控 SOURCE_DIR
   新文件到达 → 触发daily_incremental.py

② 定时兜底（每日两次）
   cron: 0 9 * * *  → daily_incremental.py --all
   cron: 0 18 * * * → daily_incremental.py --all

③ 手动触发
   hermes> 处理新录音
```

### 13.3 orchestrator.py 职责

```python
# 伪代码
def orchestrator():
    while True:
        # 1. 检查新文件（事件驱动）
        new_files = detect_new_files()
        if new_files:
            process(new_files)
        
        # 2. 定时兜底（每5分钟检查一次）
        if should_run_scheduled():
            process_all()
        
        sleep(300)
```

### 13.4 部署方式

```bash
# 守护进程启动（nohup防止挂起）
nohup python3 orchestrator.py > orchestrator.log 2>&1 &

# cron定时（兜底）
0 9,18 * * * cd ~/.hermes/pj001_pipeline && python3 daily_incremental.py --all >> logs/daily.log 2>&1
```
