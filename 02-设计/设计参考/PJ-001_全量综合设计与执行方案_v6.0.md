# PJ-001 个人知识积累工程 · 全量综合设计与执行方案 v6.0

> **一句话**：把王老师20年产业金融创业经验编译成可持续运行的个人知识操作系统——支持决策、辅助表达、传承认知。
> **核心原则**：先服务现实，再服务愿景 | 先沉淀判断，再追求全面 | 先形成复用价值，再扩大规模

---

## 第一部分：项目底层的「三个为什么」

### 1.1 为什么做这件事

不是做一个文档整理项目——市场上有无数笔记工具+AI能做到转写和摘要。

**这个项目的本质是：把认知资产化。**

- 跑过100多家银行，知道每家审批偏好、风控逻辑——这是资产
- 做过从0到1再到10的创业，知道什么模式能跑通——这是资产
- 跟数百个行业人物打交道，知道谁有什么资源、谁跟谁有关系——这是资产

这些资产现在在你脑子里。项目的目标是：把它们提取出来、结构化存储、持续迭代。

### 1.2 三个业务价值点

| 价值点 | 具体场景 | 如果做成了 |
|:-------|:---------|:-----------|
| **决策支持** | 见银行前，知识库告诉你"上次跟这家银行聊到什么程度、他们关注什么" | 少走弯路，每次沟通都有历史参考 |
| **表达增强** | 写朋友圈/见投资人时，知识库提供结构化的观点素材 | 不需要每次从零组织语言 |
| **认知传承** | 合伙人/员工/未来数字人能够理解你的业务逻辑 | 你的经验不再只是你一个人的 |

### 1.3 不做边界

| 不是 | 是 |
|:-----|:----|
| 不是知识管理工具选型 | 是用已有工具（Obsidian）解决知识沉淀问题 |
| 不是学术论文知识库 | 是**创业决策支持**系统，聚焦判断和行动 |
| 不是简单录音转文字 | 是录音→判断→决策→行动的完整链路 |
| 不是一次交付 | 是5-10年持续生长的知识生命体 |

### 4.2 🔧Sources弱化（GPT吸收）

**不再有独立的 `WIKI/Sources/` 目录。** Sources信息合并到Meeting页的元数据中。

每个Meeting页通过 `source_ref` 字段回溯到RAW中的原文文件：
```yaml
source_ref: "RAW/transcripts/20240613_陈瑛沟通贷转票_原文.md"
```

录音摘要信息直接嵌入Meeting页的 `## 基本信息` 板块，不单独建来源页。

### 4.3 🔧Meeting提升为时间入口

Meeting页是所有知识查询的**第一切入点**：

```
用户问"上次聊了什么"
    ↓
    Meeting页（时间线索引）
    ↓
    → 指向Person/Organization/Concept/Judgment/Decision
```

Meeting页的独立功能：
- 按时间排序的会议索引
- 关联人物/机构的交叉引用
- 支撑"最近发生了什么"快速回溯

### 4.5 五步深度提取法

```
Step 1: 全文扫描 + 5类标注
  [F]事实 — [J]判断 — [V]愿景 — [R]关系 — [A]行动

Step 2: 穷尽追问（对每条标注）
  [J] → "为什么？证据是什么？谁说的？"
  [V] → "怎么落地？障碍？时间表？"
  [R] → "什么关系？强度？怎么认识的？"
  [A] → "谁负责？截止时间？结果？"

Step 3: 关联已有知识
  ← 人物：检查已有person页，追加或新建
  ← 概念：检查已有concept页，追加evolution
  ← 判断：检查已有judgment，追加evolved_from
  ← 冲突：方向相反时标记conflict

Step 4: 价值分级
  S → 驱动业务方向 → 必建独立页
  A → 影响执行 → 必建或追加
  B → 辅助参考 → 写入meeting即可
  C → 上下文 → 保留原文

Step 5: 盲区声明（强制执行）
  "我确定提取了X条（S级Y条），不确定Z条（原因），
   我感觉可能遗漏了：______"
```

## 第五部分：12步摄入流程 + 审核确认（Ingest + Review）

### 5.1 🔧五流程体系（GPT吸收：审核独立）

v6.0从v5.0的八大机制升级为**五流程体系**：

| 流程 | 职责 | 触发方式 | 是否需用户介入 |
|:----|:-----|:---------|:--------------|
| **Ingest** | 原始材料摄取+结构化提取 | 新文件到达 | 否 |
| **Compile** | 页面草稿生成+冲突检测 | Ingest完成后 | 否 |
| **Review** | 人工审核+确认（核心防误入） | Compile完成后 | ✅ 必须 |
| **Query** | 读取+回答 | 用户提问 | 否 |
| **Lint** | 健康巡检 | 定时+事件触发 | 否（报告推送给用户） |

### 5.3 🔧三级确认机制（GPT吸收增强）

确认机制分为三级，核心原则是**30秒确认**：

| 级别 | 通过条件 | 包含内容 | 用户操作 | 耗时 |
|:----|:---------|:---------|:---------|:----:|
| **自动通过** | 无风险 | 格式化/frontmatter补齐/索引追加/低风险summary | 不需要操作 | 0秒 |
| **批次确认** | 用户扫一眼即可 | 新实体页/新judgment草案/new scenario候选/一批patch | 扫一眼判断 | ≤30秒 |
| **强制确认** | 必须本人点头 | 覆盖高价值判断/标记冲突/删除合并页/数字人对外内容 | 逐条确认 | ≤30秒/条 |

**30秒确认原则**：任何一次确认动作，如果超过30秒才能完成，说明确认粒度太粗或流程太重。必须确保"看一眼就能判断"。

### 5.4 各录音类型的处理差异

| 环节 | 演讲/行业认知 | 业务深度讨论 | 销售/市场类 | 管理/运营类 | 合作/投资类 |
|:-----|:-------------|:-------------|:-----------|:-----------|:-----------|
| **视角** | 演讲者 | 行业专家 | 销售市场 | CEO | 合作伙伴 |

## 第七部分：九大运行机制（🔧GPT吸收：审核独立+Query层级化）

> v5.0为"八大机制"，v6.0根据GPT评审建议将Review独立为第五流程，形成**九大机制**。

### 7.1 🔧五流程体系总揽（GPT吸收：审核独立）

整个系统由5条核心流程驱动，Review从附属动作升级为独立中枢：

```
                  ┌─────────────────┐
  新文件到达 →    │   Ingest流程    │  ← 原始材料摄取+结构化提取
                  └────────┬────────┘
                           ↓
                  ┌─────────────────┐
                  │  Compile流程    │  ← 页面草稿生成+冲突检测
                  └────────┬────────┘
                           ↓
                  ┌─────────────────┐
           ┌──→   │   Review流程    │  ← 🆕 独立审核中枢，非附属动作
           │      └────────┬────────┘
           │               ↓
  用户提问  │      ┌─────────────────┐
      │    │      │    Query流程    │  ← 读取+回答
      │    │      └─────────────────┘
      │    │
      │    └──────→   Lint流程       ← 定时巡检（发现问题→通知→修复）
      └──────────────────────────────────→ 问题进入Review重新裁决
```

### 7.2 摄入机制（Ingest）
- 接收录音/文档/外部资料 → 场景识别 → 角色视角选择 → 执行12步提取
- 编译输出到SYSTEM/compiler/extracts/（不直接落WIKI）
- 参见第五部分完整12步流程

### 7.3 编译机制（Compile）
- SYSTEM/compiler/ 作为编译层，state.json追踪SHA256增量
- 触发条件：
  - 新录音完成 → 异步立即触发
  - 王老师手动触发 → 立即执行
  - 新文档导入 → 30分钟后批量处理
  - 定时兜底 → 每24小时

### 7.4 🔧独立审核机制（Review）— 新独立

Compile产出 → 不直接写入WIKI，进入审核队列：

```
Compiler产出
    ↓
进入review_queue：
├─ 自动通过（format/frontmatter/低风险summary）→ 直接写入
├─ 批次确认（新实体/judgment草案/scenario候选）→ 用户30秒扫一眼
└─ 强制确认（覆盖高价值判断/冲突标记/删除合并/数字人对外内容）→ 逐条确认
    ↓
用户确认后 → 写入正式WIKI
    ↓
更新index + log + 变更记录
```

### 7.5 冲突检测机制（Objection）

| 级别 | 触发条件 | 处理 |
|:----:|:---------|:-----|
| L1字段 | 同一实体同一字段值不同 | 自动标记，无需人工 |
| L2语义 | 同主题判断方向相反 | 写入SYSTEM/queue/conflicts/，待裁决 |
| L3演变 | 同主题不同时间有差异(>90天) | 追加evolved_from，不标记矛盾 |
| L4证据 | 同一判断支持和反对证据并存 | 合并到evidence+counter |
| L5盲区 | 判断无evidence_chain | 标注gap，写入队列 |

**矛盾通知策略：**
- L1 → 自动处理，不入通知
- L2（S级）→ 飞书即时推送
- L2（A级）→ 每日摘要报告
- L2（B/C级）→ 每周Lint报告

### 7.6 🔧层级化查询机制（Query）— GPT吸收增强

用户提问后走标准化5步检索路径：

```
Step1: 识别问题类型
  查事实 / 查判断 / 查关系 / 查决策线索
  ↓
Step2: 读index.md → 定位目标页面（不走全库扫描）
  ↓
Step3: 深读优先级：Judgments > Decisions > Entities > Meetings
  ↓
Step4: 输出回答时明确
  - 来源引用
  - 置信度标注
  - F/J/V区分
  ↓
Step5: 若产生新洞察 → 进入Synthesis草案（建议是否回存）
```

**查询过滤**：按5种视角(speaker/expert/sales/ceo/partner) / sensitivity / 领域检索

### 7.7 审核队列机制（Review Queue）

```
SYSTEM/queue/
├── speakers/    ← 待确认发言人（每次录音后）
├── entities/    ← 候选实体名称不确定（每天审核）
├── concepts/    ← 候选概念质量一般（每周审核）
├── conflicts/   ← 待裁决矛盾（每天审核）
└── publish/     ← 待发布内容（按需）
```

### 7.8 Lint健康巡检机制（12项）

| 检查项 | 描述 | 优先级 |
|:------:|:-----|:------:|
| 孤儿页 | 无入站链接 | P1 |
| 断链 | [[wikilink]]指向不存在页面 | P0 |
| 矛盾 | 同一主题冲突信息未处理 | P0 |
| 过期 | >90天未更新 | P2 |
| 无来源 | 无source_ref | P0 |
| 无标签 | 缺少tags | P2 |
| 过长 | >200行 | P2 |
| 敏感度泄漏 | highly-sensitive被public引用 | P0 |
| 判断无来源 | Judgment的source_ref为空 | P0 |
| 实体重复 | 同一实体多个页面 | P1 |
| 数字人覆盖度 | DigitalHuman文件是否有实质内容 | P1 |
| 命名冲突 | 同一实体不同名称未统一 | P1 |

**三级巡检策略：**
- 每日轻巡检：编译失败、frontmatter缺失、新断链
- 每周标准巡检：命名冲突、关系断裂、无来源
- 每月深巡检：矛盾主题汇总、陈旧judgment、别名归一

## 第十部分：安全治理原则

### 10.1 实名处理规则

| 内容 | 规则 |
|:-----|:-----|
| **本人（王红平）** | 所有文档、对话、代码中统一用"王老师" |
| **其他人名/机构（内部）** | 知识库保持实名（不影响业务识别） |
| **对外发送**（GPT/Claude等外部模型） | 所有人名→脱敏，机构名→"某银行"等 |
| **录音/个人隐私** | 不轻易对外暴露文件名和原文 |

### 10.2 三级安全策略

| 层级 | 覆盖范围 | 处理规则 |
|:-----|:---------|:---------|
| **内部流转** | 知识库、项目文件、本地脚本 | 实名保留，凭据仅存环境变量 |
| **人机对话** | 飞书/微信对话记录 | API Key/密码自动脱敏 |
| **对外发送** | GPT/Claude/Gemini等外部模型 | 全部实名→脱敏，敏感信息不得出现 |

### 10.3 信息分类与保护等级

| 类别 | 等级 | 示例 | 处理规则 |
|:-----|:----:|:-----|:---------|
| **凭据** | 🔴 最高 | API Key、数据库密码 | 仅存环境变量，对话中不可见 |
| **本人实名** | 🟠 高 | 王红平 | 所有文档统一用"王老师" |
| **他人实名** | 🟡 中 | 业务伙伴、团队成员 | 内部保留，对外脱敏 |
| **业务敏感** | 🟡 中 | 客户名单、风控策略 | 按sensitivity标签控制传播 |
| **公共信息** | 🟢 低 | 行业知识、技术方案 | 正常使用 |

### 10.4 知识纯净度隔离（三重隔离）

| 隔离层 | 方式 | 说明 |
|:------|:-----|:------|
| **第一重：目录隔离** | RAW / WIKI / SYSTEM 物理分离 | 不易混淆 |
| **第二重：Frontmatter字段** | `knowledge_tier` + `purity` + `sensitivity` | 查询时过滤 |
| **第三重：查询白名单** | 默认只读CoreInternal，TempReference不参与回答 | 防止外部知识污染内化判断 |

### 10.5 对外安全检查清单

**每次向外部模型发送内容前，必须逐项检查：**
```
□ API Key → 已替换为 *** 或 $变量名
□ 数据库密码 → 已替换
□ 王老师实名 → 对外用"创始人"/"用户"
□ 其他人名 → 已脱敏（银行方A等）
□ 机构名 → 已脱敏（某银行等）
□ 手机号/身份证 → 已去除
```

### 10.6 🔧风险清单（GPT吸收扩展）

| # | 风险 | 现象 | 解法 |
|:-:|:-----|:-----|:-----|
| 1 | 只讲愿景不跑闭环 | 架构写20页，没一个真实问答 | 第一周闭环试点 |
| 2 | AI直接写库（幻觉落盘） | 判断有误直接进入正式WIKI | Review审核层 |
| 3 | 页面碎片化失控 | 页面多但连不成知识网 | 强索引+MOC+固定业务入口 |
| 4 | 用户审核负担重 | 每次确认很麻烦→用户不用 | 30秒确认原则+三级确认 |
| 5 | 外部知识污染内化判断 | 行业报告观点混入个人判断 | 三重隔离 |
| 6 | Token成本失控 | 长文全量处理→费用飙升 | 两步半+patch+分层价值 |
| 7 | 知识脱离业务 | 存了很多从来不查 | 嵌入"见银行前/见客户前"场景 |

### 10.7 🔧Token成本控制策略（GPT吸收新增）

| 策略 | 说明 | 适用场景 |
|:----|:-----|:---------|
| **长文切块** | >5000字的长录音切段处理 | 超长录音 |
| **两步半** | 先出结构化JSON再生成页面，可复用 | 所有Ingest |
| **patch更新** | 已有实体只更新增量部分，不全文重写 | 已有实体更新 |
| **分层价值处理** | S/A级内容深处理，B/C级只做meeting摘要 | 所有录音 |
| **缓存编译结果** | SHA256追踪不变的文件不重处理 | 重复Ingest |
