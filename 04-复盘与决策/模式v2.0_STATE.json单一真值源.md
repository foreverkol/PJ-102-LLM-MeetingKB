## 🎯 v1.0 模式的问题诊断

王老师语音原话:"前后脱钩、整体计划走到哪一步都不明确、为什么是这个模式、有没有更好更优化的、更专业、更适合实际情况的、高质量产出的"

### 实测数据

| 维度 | v1.0 现状 | 问题 |
|---|---|---|
| `04-复盘与决策/*.md` | **62 份** 散落文档 | 无主索引,需翻 3-5 份才能拼 Sprint 全貌 |
| `STATE.md` | **415 行**,Sprint 出现 57 次 | 滚雪球式追加,**只反映过去不指引未来** |
| Sprint 编号 | Sprint 1-21 + M0-M5 + T-01~T-14 **三层并行** | 互相交织,新会话找不到"现在到哪" |
| 决策点 | 5 项散在 4 份文档(E 选项报告 / STATE.md / T-* / 路线图) | 找不到"现在要做什么" |
| 文档生成 | STATE.md 手写,容易过时 | 文档和实际状态漂移 |

### 根本原因

**当前模式是"文档驱动"**:
```
王老师说 → 我写一份文档 → 文档成历史 → 没人维护 → 下次会话查不到
```

**核心矛盾**:
- 文档是"主体"(人写给人看)
- 文档是"历史"(写完就过时)
- 文档是"分散"(同一事实多处写)

## 🏗 v2.0 模式核心:**STATE.json 单一真值源**

### 核心原则

```
STATE.json = 机器可读单一真值源(主体)
STATE.md   = STATE.json 的 markdown 视图(副作用,自动生成)
其他文档   = STATE.json 的派生(按需生成,不持久化)
```

### 状态机定义(STATE.json schema)

```json
{
  "$schema": "PJ-102-STATE-v1",
  "version": "v3.1.0-stable",
  "tag": "v3.1.0-stable",
  "branch": "dev",
  "ahead_of_main": 25,
  "last_updated": "2026-09-06 10:09:14 +0800",
  "last_commit": { "hash": "...", "subject": "..." },
  
  "current_sprint": "Sprint 22",
  "current_sprint_status": "M0-planning(等王老师批决策项)",
  
  "previous_sprint": {
    "id": "Sprint 21",
    "version": "v3.1.0-rc1 → v3.1.0-stable",
    "metrics": { "L1_tests": "98 passed in 3.27s", ... }
  },
  
  "pending_decisions": [
    { "id": "DT-01", "priority": "P0", "title": "...", "blocker": "...", ... },
    ...
  ],
  
  "do_now": ["1. ...", "2. ...", "3. ..."],
  "mode_architecture": { "version": "v2.0", ... },
  "protocols": { "v41": "OK", ... }
}
```

### 自动生成流程

```
git log + 实测文件系统 + L1 测试
        ↓
   STATE.json(主体)
        ↓
state_to_md.py(自动生成)
        ↓
   STATE.md(133 行,可读视图)
```

## 🎓 与 Superpower 方法论的关系

本模式是 `ai-assisted-project-engineering` 元方法论的实例化:

| 元方法论 | v2.0 模式对应 |
|---|---|
| 阶段 1:需求 | `pending_decisions` + `do_now`(机器可读决策) |
